# 🗄️ Архитектура интеграции с базой данных Synology Photos

Этот документ описывает методы прямого взаимодействия с внутренней базой данных Synology Photos (`synofoto`) для мониторинга изменений в альбомах. 

Например я использую эту возможность для работы с общими семейными альбомами, я интегрировал свой сервис с Matrix Elements для получения уведомлений о публикации  новых альбомов, добавления новых фото и тп. Это очень удобно при общем использовании альбомов.

Ты можешь использовать эту возможность для своих нужд, но я просто не хочу, чтобы продленная работа не потерялась дома в тумбочке. 

> [!IMPORTANT]
> Сервис **не использует** Synology Web API (`/webapi/entry.cgi`). Прямое чтение из PostgreSQL через Unix Socket обеспечивает максимальную надежность, скорость и независимость от изменений в недокументированном API Synology.

## 🔌 Параметры подключения

| Параметр | Значение | Описание |
| :--- | :--- | :--- |
| **Тип подключения** | Unix Domain Socket | Обходит сетевые ограничения, работает локально |
| **Путь к сокету** | `/var/run/postgresql` | Стандартный путь в DSM |
| **Имя базы данных** | `synofoto` | Внутренняя БД приложения Synology Photos |
| **Пользователь** | `postgres` | Требует прав доступа контейнера к сокету (обычно `root` или группа `postgres`) |

## 📊 Схема ключевых таблиц

Для мониторинга шаринга и медиа используются 5 основных таблиц:

| Таблица | Описание | Ключевые поля |
| :--- | :--- | :--- |
| **`album`** | Метаданные альбомов | `id`, `id_user` (владелец), `name`, `shared` (bool), `passphrase_share`, `create_time`, `item_count` |
| **`share`** | Настройки публичного доступа | `passphrase` (PK), `privacy_type` (0=частный, 1=просмотр, 2=скачивание), `hashed_password`, `expired_time`, `enable` |
| **`share_permission`** | Права доступа пользователей | `passphrase_share`, `target_type` (1=пользователь), `target_id` (ID получателя), `id_user` (ID владельца) |
| **`user_info`** | Пользователи системы DSM | `id` (PK), `name` (логин), `uid` |
| **`unit`** | Метаданные медиафайлов | `id` (PK), `type` (1=фото, 2=видео), `filename`, `createtime` |

## 💻 Основные SQL-запросы

### 1. Получение списка расшаренных альбомов и настроек
Этот запрос собирает полную картину: владелец, получатели и параметры конфиденциальности.

```sql
SELECT
    a.id AS album_id,
    a.name AS album_name,
    a.passphrase_share,
    owner_ui.name AS owner_name,
    recipient_ui.name AS shared_to_name,
    recipient_ui.uid AS shared_to_uid,
    a.create_time AS album_create_time,
    a.item_count,
    s.privacy_type,
    s.hashed_password,
    s.expired_time
FROM album a
JOIN user_info owner_ui ON a.id_user = owner_ui.id
JOIN share_permission sp ON a.passphrase_share = sp.passphrase_share
JOIN user_info recipient_ui ON sp.target_id = recipient_ui.id
LEFT JOIN share s ON a.passphrase_share = s.passphrase
WHERE a.shared = true
  AND sp.target_type = 1
  AND a.id_user != sp.target_id
ORDER BY a.id, recipient_ui.name;
```

### 2. Получение списка медиафайлов в альбоме
Используется для детекции добавления новых фото/видео. 

> [!WARNING]
> Запрос жестко ограничен `LIMIT 500` и сортировкой по убыванию времени создания. Это защитный механизм от переполнения памяти (OOM) при обработке альбомов с тысячами файлов. Бизнес-логика отслеживает только последние добавленные элементы.

```sql
SELECT
    u.id AS unit_id,
    u.type AS media_type
FROM album a
JOIN share_permission sp ON a.passphrase_share = sp.passphrase_share
JOIN unit u ON u.id = sp.target_id -- *Связь может варьироваться в зависимости от версии DSM*
WHERE a.id = {album_id}
ORDER BY u.createtime DESC
LIMIT 500;
```

## ⚙️ Пайплайн обработки данных (Data Pipeline)

Чтобы корректно отслеживать изменения и избегать ложных срабатываний, данные обрабатываются в строгом порядке:

1. **Raw Fetch (Сырой запрос):** Выполняется SQL-запрос №1. Результат — плоский список строк (один альбом может встречаться несколько раз, по количеству получателей).
2. **Aggregation (Группировка):** Плоский список преобразуется в словарь (Map) по ключу `album_id`. Метаданные альбома перезаписываются, а получатели добавляются в массив `shared_to`.
3. **State Sync (Синхронизация состояния):** Сгруппированные данные сравниваются с локальным кэшем (`state.json`).
   - *Новый альбом:* Есть в БД, нет в кэше.
   - *Отозванный доступ:* Есть в кэше, нет в БД (удаляется из кэша).
4. **Media Diff (Детекция новых медиа):** Для каждого активного альбома выполняется SQL-запрос №2. Извлеченные `unit_id` сравниваются с массивом `known_photo_ids` в кэше. Новые элементы подсчитываются раздельно для фото и видео. Удаленные элементы удаляются из кэша.
5. **State Update (Обновление кэша):** После генерации событий (уведомлений) локальный `state.json` перезаписывается актуальными данными. Фиксируется `last_check_time`.

## ⚠️ Особенности и ограничения

- **Хэши паролей:** Поле `hashed_password` содержит только хэш. Узнать или передать пользователю исходный пароль невозможно. Можно только констатировать факт его наличия.
- **Таймстампы:** Все поля времени (`create_time`, `expired_time`, `createtime`) хранятся в формате Unix Epoch (секунды). Требуют конвертации на стороне приложения.
- **Совместимость:** Прямой доступ к БД жестко привязан к схеме PostgreSQL. При крупных мажорных обновлениях DSM схема таблиц может измениться, что потребует адаптации запросов.
